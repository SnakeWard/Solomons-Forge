# Handoff: 0.9.0 Release Candidate

Milestone 4 of 5 on the road to 1.0. See docs/roadmap/README.md for the
protocol rules that govern this handoff.

## Receiving Actor
- Target: AI coding agent or maintainer working in the Forge repository
- Why this target: finishes conformance and packaging so 1.0 is only a
  freeze and a version bump
- Expected role: Implementer, with a separate reviewer role for the spec
  freeze in step 7

## Context
- Project: Forge, a framework for governed AI-assisted software construction
- Current state: gate runner: planned (0.7.0). Attestation log: planned
  (0.8.0). Both must be merged first. HC-3 conformance: planned (defined in
  spec, not implemented). Invariant-to-check map required by INV-11: planned.
  Installable command-line tool: planned (package has no bin, files, or exports).
- Current goal: close every remaining gap between what the specs claim and
  what the tools enforce
- Build environment: Node 20 or later, zero runtime dependencies

## Target Outcome
HC-3 is mechanically checkable. Every core invariant maps to a mechanical
check or to recorded known debt. `npm pack` produces an installable package
whose `forge` command exposes every tool. All five specifications are marked
Release Candidate.

## Non-Negotiable Constraints
- HC-3 is defined in the handoff contract §4. This milestone implements that
  definition and does not redefine it.
- Existing npm scripts keep working as aliases of the new command.
- No new runtime dependencies. No `npm publish`.

## Preservation Map
- Do not modify: HC-1 and HC-2 validator behavior, receipt, gate, and
  attestation formats.
- Preserve: every existing npm script name and exit code.
- Preserve: all existing tests and harness scenarios unchanged.

## Required Task Steps
1. HC-3: add an HC-3 level to spec/handoff-conformance.json. Add
   `--level HC-3 --contract FILE` to the handoff validator. It must require
   that every Validation Checklist item maps to a claim in the acceptance
   contract, and that each such claim references at least one check.
   Unmapped items fail. Add tests.
2. Write spec/invariant-enforcement.json mapping INV-1 to INV-11 to their
   enforcing checks (linter, validator, gate, test, or receipt). Mark each
   unenforced invariant as `known_debt` with a reason. Add a test that fails
   if any invariant is missing from the map.
3. Add src/cli.js as a `forge` command with subcommands validate, bind,
   receipt, gate, attest, and lint. Add `bin`, `files`, and `exports` to
   package.json, and repoint the npm scripts to it.
4. Add a CI job that runs `npm pack`, installs the tarball into an empty
   directory, and runs `forge --help` and `forge validate` on an example.
5. Reconcile every spec's Security Considerations or Trust Boundary with
   SECURITY.md.
6. Set every spec's Status to Release Candidate. Set versions to 1.0.0-rc.1,
   except where a spec is already at 1.0.0.
7. Reviewer pass: read all five specs together and list contradictions,
   undefined terms, and MUST-level requirements that have no check. Fix them
   or record them in the enforcement map as known debt.
8. Update README and CHANGELOG, then release 0.9.0 per protocol rule 5.

## Forbidden Behaviors
- Do not modify or delete failing tests or checks to achieve a passing state.
- Do not mark an invariant as enforced without naming the check that fails
  when the invariant is violated.
- Do not add features beyond this list; new ideas go to Deferred in the
  roadmap README.

## Output Format
A single pull request with the Validation Checklist results, the reviewer's
findings list from step 7, and the `npm pack` file listing.

## Validation Checklist
- [ ] `forge validate --level HC-3` passes on an example with a matching
  contract and fails when a checklist item is not mapped.
- [ ] The invariant map test passes, and every INV entry has a check or a
  known_debt reason.
- [ ] The packed tarball installs into an empty directory and `forge --help`
  lists all six subcommands.
- [ ] `npm run gate` passes on ubuntu-latest and windows-latest.
- [ ] Every spec shows Status Release Candidate.
- [ ] All previously passing tests and harness scenarios still pass.

## Failure Recovery
If blocked: state what blocked completion, separate confirmed facts from
assumptions, leave existing formats and scripts untouched, propose the
smallest safe next step, and stop.
