# Handoff: 1.0.0 Release

Milestone 5 of 5 on the road to 1.0. See docs/roadmap/README.md for the
protocol rules that govern this handoff.

## Receiving Actor
- Target: the maintainer, assisted by an AI coding agent for the diff
- Why this target: the stability promise and the tag are the maintainer's
  decisions. The agent prepares, and the maintainer accepts.
- Expected role: Implementer for the diff. The maintainer is the reviewer
  and makes the final acceptance.

## Context
- Project: Forge, a framework for governed AI-assisted software construction
- Current state: 0.9.0 release candidate: planned (must be merged, with no
  open defects against the specs). All five specs at Release Candidate:
  planned. Installable forge command-line tool: planned.
- Current goal: declare the specifications and command-line interface stable
  under Semantic Versioning
- Build environment: Node 20 or later, zero runtime dependencies

## Target Outcome
Version 1.0.0 is merged and tagged. All specifications are Stable. A
compatibility policy states what counts as a breaking change. The release is
accepted through an acceptance receipt produced by Forge's own tooling, with
the result appended to an attestation log.

## Non-Negotiable Constraints
- No behavior changes in this milestone. Only status, version, and
  documentation text change.
- The acceptance receipt for the release must report verified, not disputed
  or unchecked.

## Preservation Map
- Do not modify: any file under src/, harness/, or test/.
- Preserve: every 0.9.0 format, command, and exit code exactly.

## Required Task Steps
1. Confirm that no issue opened since 0.9.0 is labeled as a spec defect. If
   one is, stop and release 0.9.x instead.
2. Set every spec's Status to Stable and its Version to 1.0.0.
3. Add docs/compatibility.md. It defines a breaking change as any change
   to a spec MUST-level requirement, a JSON format field, a command-line
   flag, or an exit code. Breaking changes require a major version.
4. Bump package.json to 1.0.0, write the dated `[1.0.0]` CHANGELOG section,
   and update the README Status paragraph.
5. Write docs/roadmap/release-contract.json with one claim per 1.0 criterion
   in the roadmap README, each mapped to a gate check. Bind it with
   `forge bind`, then run `forge receipt` with every check selected and
   `--attest`.
6. Attach the receipt and verified attestation log to the pull request. The
   maintainer reviews them, merges, and creates the annotated tag v1.0.0.

## Forbidden Behaviors
- Do not modify or delete failing tests or checks to achieve a passing state.
- Do not include feature work or refactors in the release pull request.
- Do not create the tag or publish the package; the maintainer does both.

## Output Format
A single pull request containing the diff, receipt.json, receipt.md, and
the attestation log, with the Validation Checklist results in its
description.

## Validation Checklist
- [ ] `npm run gate` exits 0 on ubuntu-latest and windows-latest.
- [ ] `npm run lint:spec` passes and every spec shows Status Stable and
  Version 1.0.0.
- [ ] The release receipt reports verified for every claim.
- [ ] `forge attest verify` exits 0 on the attached log.
- [ ] `git diff v0.9.0 -- src harness test` is empty.
- [ ] docs/compatibility.md exists and README links to it.

## Failure Recovery
If blocked: state what blocked completion, separate confirmed facts from
assumptions, make no code changes, propose the smallest safe next step
(usually a 0.9.x release), and stop.
