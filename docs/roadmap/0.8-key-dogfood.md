# Handoff: 0.8.0 Forge CI Verified by Key

Milestone 3 of 4 on the Forge track to the joint beta. See
docs/roadmap/README.md for the protocol rules and the release sequence.

## Receiving Actor
- Target: AI coding agent or maintainer working in the Forge repository
- Why this target: CI integration that follows the evidence mapping
  specified in 0.7.0, using Key's existing tools
- Expected role: Implementer. Wire Key into Forge's CI exactly as the
  verification interface specifies. Do not extend the specification.

## Context
- Project: Forge, a framework for governed AI-assisted software construction
- Current state: verification interface specification: real
  (spec/verification-interface.md, 0.7.0). Its gate mapping, two routes, run
  manifest, and failure cases were trialled against the pinned Key release
  in scratch space before it was written: real. Key's tool to derive a contract from CI, its adapters,
  its run verification, and its attestation log: real (Key repository).
  Forge CI runs its checks without recording evidence: real. Key contract
  for Forge: planned. Trusted-program allowlist for Forge's CI: planned.
- Current goal: make Forge's own build pass through Key, so the construction
  layer is verified by the verification layer it depends on
- Build environment: Node 20 on ubuntu-latest, macos-latest, and
  windows-latest. Python
  3.11 or later in CI only. Key installed from the pinned release named in
  spec/verification-interface.md, with its SHA-256 checked before install.

## Target Outcome
Forge CI records Key evidence for every baseline check. It runs Key's run
verification on that evidence and fails the build if verification does not
pass. A committed Key contract and trusted-program allowlist define what
Forge's CI must prove.

## Non-Negotiable Constraints
- Key is installed only from the pinned release, and its SHA-256 is verified
  first. There are no unpinned installs and no installs from a branch.
- The Forge npm package gains no runtime dependency. Python and Key appear
  only in CI.
- Existing CI checks keep running and keep failing the build on their own.
  Key verification is an added check, not a replacement.
- Nothing is written to the Key repository.

## Preservation Map
- Do not modify: src/**, spec/**, harness/**, extensions/**.
- Preserve: all existing CI steps, their order, and the uploaded acceptance
  artifacts.
- Preserve: the ability to run every npm script without Python installed.

Scope note, added during execution: the contract and allowlists live in
key/ (key/key-contract.yaml, key/trusted-programs-PLATFORM-ARCH.sha256), and
the key-verify job pins Node.js v20.20.2 exactly, because each allowlist pins
that exact binary's hash. The job's logic is in scripts/key-verify.js so that
it runs the same way on all three operating systems and locally.

## Required Task Steps
1. Give each baseline CI step the name that derives its gate ID in
   spec/verification-interface.md §3.1 (for example "Term lint" derives
   term_lint_gate). Using Key's contract-derivation tool, generate a Forge
   contract from .github/workflows/ci.yml with the automatic gates and the
   attested acceptance_decision_gate. The tool puts every gate on one route,
   so split the result into the `ci` and `acceptance` routes of §3.1 and add
   acceptance_receipt_gate. Commit it as key-contract.yaml, and run Key's
   contract linter on it until it reports 0 errors.
2. Commit the trusted-program allowlist the tool produces. Review each entry.
   Where a runner's program hash (for example node or python) differs between
   ubuntu-latest and windows-latest, pin a separate allowlist for each
   operating system. Do not loosen the check.
3. Add a CI job, key-verify, that installs the pinned Key release after
   checking its hash, then runs each baseline check with Key's adapter as
   mapped in §3.2. The node test suite writes JUnit output for the JUnit
   adapter. Write run.json as §3.4 specifies, with `result` derived from the
   recorded decisions. Key has no command for this at the pinned release.
4. Run Key's run verification on the assembled run directory. Any finding at
   CRITICAL or ERROR fails the job.
5. Upload the run directory as a CI artifact next to the acceptance results.
6. Add a gate-bypass drill: a documented manual procedure, or a CI job that
   is expected to fail, which deletes one gate decision and confirms that
   Key names the missing gate.
7. Add docs/key-integration.md explaining how to reproduce the verification
   locally. Update README and CHANGELOG, then release 0.8.0 per protocol rule
   5.

## Forbidden Behaviors
- Do not modify or delete failing tests or checks to achieve a passing state.
- Do not classify a program decision as attested to avoid pinning its hash.
- Do not add entries to the trusted-program allowlist without reviewing the
  binary each entry names.
- Do not use `continue-on-error` or an allow-failure setting on key-verify.

## Output Format
A single pull request with the contract, allowlists, CI changes, and docs.
Its description holds the Validation Checklist results and links to a CI
run showing key-verify passing on both operating systems.

## Validation Checklist
- [ ] Key's contract linter reports 0 errors on key-contract.yaml.
- [ ] key-verify passes on ubuntu-latest and windows-latest.
- [ ] Deleting one gate decision from the run makes Key's run verification
  fail and name that gate.
- [ ] The Key install step fails when the expected SHA-256 is altered.
- [ ] `npm test` still passes on a machine without Python.
- [ ] All previously passing CI jobs still pass.

## Failure Recovery
If blocked: state what blocked completion, separate confirmed facts from
assumptions, and leave the existing CI steps untouched. If Key cannot
express something Forge's CI needs, record it under Key dependencies in
docs/roadmap/README.md, propose the smallest safe next step, and stop.
