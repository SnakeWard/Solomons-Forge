protocol rules that govern this handoff.

## Receiving Actor
- Target: AI coding agent or maintainer working in the Forge repository
- Why this target: bounded cleanup across docs, lexicon, and CI with existing
  mechanical checks to confirm each change
- Expected role: Implementer. Make the listed changes only; do not redesign.

## Target Outcome
Version 0.6.0 is merged and released. The repository contains no duplicate
docs. The lexicon and LINEAGE.md record Key as Forge's verification layer,
and README describes the two layers.
SECURITY.md and CONTRIBUTING.md exist. All baseline checks pass.

## Non-Negotiable Constraints
- MIT license only; no new runtime dependencies.
- Lexicon changes bump lexicon_version and add a policy_note entry.
- The brand allowlist stays scoped to the files it already lists unless this
  handoff names a new one.

## Preservation Map

- Preserve: all existing CLI commands, exit codes, and receipt formats.
- Preserve: docs/case-study-gates.md verbatim (incident record).

## Required Task Steps
1. Delete docs/getting-started_v2.md after confirming it is byte-identical to
   docs/getting-started.md (`git diff --no-index` shows no output).
2. Update the lexicon so the Key name is recorded as the name of the Key
   verifier repository, Forge's verification layer, which Forge may link to
   and name. Remove "reserved, not used by this repository". Admit Key's
   published command names as a scoped exception, so Forge docs can name
   them exactly (some contain a word the lexicon otherwise maps). Record
   that the lexicon's contract-file pattern matches Key's own contract file
   naming, and decide whether Forge files may use that suffix. Until that
   decision, Forge names its Key contract key-contract.yaml. Bump
   lexicon_version to 1.0.5 and add a policy_note.
3. Rewrite LINEAGE.md so it records the vocabulary mapping it claims to hold:
   a table of each lexicon entry's internal term and public term, and the
   updated Key naming note. It stays excluded from the term-leak scan.
4. Add SECURITY.md stating that the check runner is not a sandbox (acceptance
   receipt spec §5), and naming how to report vulnerabilities.
5. Add CONTRIBUTING.md covering the baseline checks, the roadmap protocol,
   and the rule that contributions touching behavior include a handoff.
   Add a "Two layers" section to README.md matching docs/roadmap/README.md.
6. Either align the extension-package job's Node version with the test job,
   or add a one-line comment in ci.yml giving the reason for the difference.
7. Move the `[Unreleased]` changelog entries into a dated `[0.6.0]` section,
   bump package.json to 0.6.0, and update the README Status paragraph.

## Forbidden Behaviors
- Do not modify or delete failing tests or checks to achieve a passing state.
- Do not add exclusions to the term-leak linter to silence a new violation.
- Do not start verification interface, Key integration, or packaging work;
  those belong to later milestones.
- Do not build a gate runner or attestation log in Forge; Key provides both.
- Do not create or push git tags; the maintainer tags releases.

## Output Format

- [ ] `npm run lint:terms` reports 0 violations.
- [ ] `npm run lint:spec` reports 0 violations.
- [ ] `npm test` passes with no fewer tests than before.
- [ ] `npm run test:acceptance` passes every scenario.
- [ ] `npm run validate:handoff` passes for every file in docs/roadmap except
  README.md.
- [ ] docs/getting-started_v2.md no longer exists and no file links to it.
- [ ] lexicon.json lexicon_version is 1.0.5 and describes the Key verifier link.
- [ ] package.json version is 0.6.0 and CHANGELOG.md has a dated 0.6.0 section.

## Failure Recovery
If blocked: state what blocked completion, separate confirmed facts from
assumptions, leave spec/** and src/** untouched, propose the smallest safe
next step, and stop.
