# Handoff: 0.8.0 Attestation Log

Milestone 3 of 5 on the road to 1.0. See docs/roadmap/README.md for the
protocol rules that govern this handoff.

## Receiving Actor
- Target: AI coding agent or maintainer working in the Forge repository
- Why this target: new specification and tool with a clear data model and
  deterministic tests
- Expected role: Builder. Specify, then implement, then test, in that order.

## Context
- Project: Forge, a framework for governed AI-assisted software construction
- Current state: gate runner: planned (0.7.0, must be merged first).
  Acceptance receipts: real, and explicitly not append-only attestations.
  Attestation log specification: planned. Attestation tooling: planned.
- Current goal: deliver the third pillar in the project description,
  append-only attestation logging, so gate results and receipts leave a
  tamper-evident record
- Build environment: Node 20 or later, zero runtime dependencies, node:crypto

## Target Outcome
spec/attestation-log.md defines a JSON Lines log in which each entry is
hash-chained to the previous one. src/attest/log.js can append entries,
verify a log, and show entries. The gate runner and receipt CLI can each
append their result to a log when given `--attest PATH`.

## Non-Negotiable Constraints
- Append-only: the tool never rewrites or deletes existing lines. It appends
  only after verifying that the existing chain is intact.
- Each entry: `schemaVersion`, `seq`, `timestamp`, `kind` (gate-result,
  acceptance-receipt, or note), `subject` (object including a hash),
  `payloadSha256`, `prevHash`, `hash`. `hash` is SHA-256 over the canonical
  JSON of the entry without `hash`. The first entry's `prevHash` is 64 zeros.
- Canonical JSON: keys in sorted order, no insignificant whitespace, UTF-8.
- Hash chaining gives tamper evidence, not authentication. Signatures are
  deferred past 1.0, and the spec must say so.
- No new runtime dependencies.

## Preservation Map
- Do not modify: existing receipt and gate output formats. `--attest` only
  adds behavior.
- Preserve: exit codes of the receipt CLI and gate runner. A failure to
  append an attestation is an operational error (exit 2) and must never turn
  a failing result into a passing one.
- Preserve: all existing tests and harness scenarios unchanged.

## Required Task Steps
1. Write spec/attestation-log.md with sections Purpose, Entry Format,
   Canonicalization and Chaining, Verification, Trust Boundary. Register it in
   spec/spec-manifest.json.
2. Implement `forge-attest append|verify|show` in src/attest/log.js, exposed
   as `npm run attest`. verify exits 0 when the chain is intact and 1 when it
   is broken, and names the first bad `seq`.
3. Add `--attest PATH` to src/gate/run.js and src/receipt/acceptance.js.
4. Add test/attestation-log.test.js covering: an empty log, the first entry,
   an intact multi-entry chain, an edited entry, a deleted entry, reordered
   entries, a truncated final line, append refused on a broken chain, and a
   deterministic hash for a fixed entry (a test vector).
5. Add the canonicalization test vector to the spec so other implementations
   can check their output against it.
6. Record in the spec that the attestation log satisfies the "attestation log
   format" companion named in spec/core-invariants.md §2.
7. Update README and CHANGELOG, then release 0.8.0 per protocol rule 5.

## Forbidden Behaviors
- Do not modify or delete failing tests or checks to achieve a passing state.
- Do not add a repair, rewrite, or compact command.
- Do not describe hash chaining as signing or authentication anywhere.
- Do not change receipt or gate pass/fail semantics.

## Output Format
A single pull request with the spec, tool, integration flags, and tests,
with the Validation Checklist results and a sample verified log in its
description.

## Validation Checklist
- [ ] `npm run lint:spec` checks 5 specs with 0 violations.
- [ ] `node --test test/attestation-log.test.js` passes every listed case.
- [ ] The spec's test vector hash matches the implementation's output.
- [ ] `npm run gate -- --attest LOG` followed by `npm run attest -- verify LOG`
  exits 0. Editing any byte in LOG makes verify exit 1.
- [ ] A receipt run with `--attest` appends one acceptance-receipt entry
  whose payloadSha256 equals the SHA-256 of receipt.json.
- [ ] All previously passing tests and harness scenarios still pass.

## Failure Recovery
If blocked: state what blocked completion, separate confirmed facts from
assumptions, leave existing output formats untouched, propose the smallest
safe next step, and stop.
