# Handoff: 0.7.0 Verification Boundary

Milestone 2 of 4 on the Forge track to the joint beta. See
docs/roadmap/README.md for the protocol rules and the release sequence.

## Receiving Actor
- Target: AI coding agent or maintainer working in the Forge repository, with
  read access to a checkout of the Key repository
- Why this target: this is specification work that has to match Key's
  existing, documented tool behavior exactly
- Expected role: Architect. Write the interface specification and align the
  existing specs with it. Do not write integration code in this milestone.

## Context
- Project: Forge, a framework for governed AI-assisted software construction
- Current state: 0.6.0 cleanup: planned (must be merged first). Core
  invariants name "gate definitions" and an "attestation log format" as
  companion specifications: real, but neither exists in Forge. Key provides
  gate decisions, an exit-code, JUnit, and SARIF adapter, an append-only
  attestation log, tree pinning, and run verification: real (Key repository,
  release v0.10.1). Acceptance receipt spec §5 says no adapter to Key exists:
  real. Forge-to-Key interface specification: planned.
- Current goal: settle which layer owns each duty, and specify exactly how
  Forge outputs become Key evidence, before any integration code is written
- Build environment: Node 20 or later, zero runtime dependencies. Key needs
  Python 3.11 or later, PyYAML, and jsonschema; it is used only for reading
  its documentation in this milestone.

## Target Outcome
spec/verification-interface.md exists and is registered in the spec manifest.
It assigns every duty in the core invariants to Forge or Key, and gives an
exact mapping from each Forge check to a Key adapter call. The core invariants
and acceptance receipt specs point to it instead of to missing companion
specifications or a "future adapter". README no longer lists a gate runner or
attestation tooling as planned Forge work.

## Non-Negotiable Constraints
- The spec describes Key's commands only as Key documents them at the pinned
  release. It must not invent Key flags or formats.
- Mapping fails closed: every nonzero Forge exit code, including 2
  (operational error), maps to a failing Key gate decision.
- Forge keeps zero runtime dependencies. Key appears only as an optional,
  external verification layer.
- Spec edits that change meaning bump that spec's version. Wording-only
  clarifications do not.

## Preservation Map
- Do not modify: src/**, test/**, harness/**, extensions/**, receipt JSON
  format, contract format, CLI exit codes.
- Preserve: the acceptance receipt's own trust boundary statements. Key
  integration adds verification and does not widen what a receipt claims.
- Preserve: every existing check in CI.

## Required Task Steps
1. Read Key's README, trust boundary document, and exit-code adapter usage at
   release v0.10.1. Record the release version and artifact SHA-256 in the
   new spec.
2. Write spec/verification-interface.md with sections Purpose, Layers and
   Responsibilities, Evidence Mapping, Pinning, and Trust Boundary. Use the
   standard metadata block (Specification, Version 0.1.0, Status Draft,
   License).
3. Layers and Responsibilities: a table assigning each of INV-1 to INV-11,
   plus gate decisions, the attestation log, tree pinning, and run
   verification, to Forge, Key, or both, with one sentence of reason for each.
4. Evidence Mapping: for each Forge check (lint:terms, lint:spec,
   validate:handoff, the node test suite, test:acceptance, receipt CLI), give
   the Key adapter mode and gate name. Use JUnit for the node test suite
   (node's built-in junit reporter) and exit-code for the rest.
5. Explain how an acceptance contract's pinned revision and file hashes relate
   to Key's tree pin. They are separate identities. State which one each
   layer checks, and do not merge them.
6. Update spec/core-invariants.md §2 so the gate and attestation companion
   specifications are provided by Key through this interface. Bump its version
   to 0.2.0.
7. Update spec/acceptance-receipt.md §5 to link the new spec instead of "a
   future adapter". This is a wording-only change, so the version stays.
8. Register the new spec in spec/spec-manifest.json. Update the README Status
   paragraph and CHANGELOG, then release 0.7.0 per protocol rule 5.

## Forbidden Behaviors
- Do not modify or delete failing tests or checks to achieve a passing state.
- Do not implement a gate runner, attestation log, or Key adapter in Forge.
- Do not describe Key guarantees larger than Key's own trust boundary
  document states.
- Do not edit the Key repository.

## Output Format
A single pull request with the spec changes and README and CHANGELOG
updates, with the Validation Checklist results in its description. It must
also list every Key command the spec references, with the Key file where
that command is documented.

## Validation Checklist
- [ ] `npm run lint:spec` checks 4 specs with 0 violations.
- [ ] `npm run lint:terms` reports 0 violations.
- [ ] Every INV from 1 to 11 appears exactly once in the responsibilities
  table.
- [ ] Every Key command in the spec appears in Key's README or `--help`
  output at the pinned release.
- [ ] README no longer lists a Forge gate runner or attestation tooling as
  planned.
- [ ] All previously passing tests and harness scenarios still pass.

## Failure Recovery
If blocked: state what blocked completion, separate confirmed facts from
assumptions, and leave code untouched. If Key lacks something the mapping
needs, record it under Key dependencies in docs/roadmap/README.md, propose
the smallest safe next step, and stop.
