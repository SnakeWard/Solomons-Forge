# Handoff: 0.9.0 Public Beta

Milestone 4 of 4 on the Forge track to the joint beta. See
docs/roadmap/README.md for the protocol rules and the release sequence.

## Receiving Actor
- Target: AI coding agent or maintainer working in the Forge repository
- Why this target: closes the gaps between what the specs claim and what the
  tools enforce, and makes Forge installable for real users against a pinned
  Key beta
- Expected role: Implementer, with a separate reviewer role for the spec
  review in step 9

## Context
- Project: Forge, a framework for governed AI-assisted software construction
- Current state: verification interface: planned (0.7.0). Forge CI verified
  by Key: planned (0.8.0). Both must be merged first. Key 0.11.0b1 on PyPI:
  planned (Key track, must be released first). HC-3 conformance: planned
  (defined in spec, not implemented). Invariant-to-check map required by
  INV-11: planned. Installable command-line tool: planned (package has no
  bin, files, or exports).
- Current goal: a hardened public beta that a new user can install and use
  through the whole workflow, with Forge and Key working together
- Build environment: Node 20 or later, zero runtime dependencies. Python 3.11
  or later and Key 0.11.0b1 in CI only.

## Target Outcome
Forge 0.9.0 is released as a public beta. HC-3 is mechanically checkable.
Every core invariant maps to a mechanical check or to recorded known debt.
`npm pack` produces an installable package whose `forge` command exposes
every Forge tool. A joint end-to-end test proves the full user workflow
through Forge and Key 0.11.0b1 on Linux, macOS, and Windows. All four specs
are marked Beta.

## Non-Negotiable Constraints
- HC-3 is defined in the handoff contract §4. This milestone implements that
  definition and does not redefine it.
- Existing npm scripts keep working as aliases of the new command.
- No new runtime dependencies. No `npm publish` by the receiving actor.
- Key is installed from PyPI at exactly 0.11.0b1, with hash checking.

## Preservation Map
- Do not modify: HC-1 and HC-2 validator behavior, receipt and contract
  formats, gate names in key-contract.yaml.
- Preserve: every existing npm script name and exit code.
- Preserve: all existing tests and harness scenarios unchanged.

## Required Task Steps
1. HC-3: add an HC-3 level to spec/handoff-conformance.json. Add
   `--level HC-3 --contract FILE` to the handoff validator. It must require
   that every Validation Checklist item maps to a claim in the acceptance
   contract, and that each such claim references at least one check.
   Unmapped items fail. Add tests.
2. Write spec/invariant-enforcement.json mapping INV-1 to INV-11 to their
   enforcing checks (Forge linter, validator, test, or receipt, or a Key rule
   named by its rule ID at the pinned Key release). Mark each unenforced
   invariant as `known_debt` with a reason. Add a test that fails if any
   invariant is missing from the map.
3. Add src/cli.js as a `forge` command with subcommands validate, bind,
   receipt, and lint. Do not wrap Key's tools. Add `bin`, `files`, and
   `exports` to package.json, and repoint the npm scripts to it.
4. Add a CI job that runs `npm pack`, installs the tarball into an empty
   directory, and runs `forge --help` and `forge validate` on an example.
5. Add examples/joint-workflow/, a small sample project, and a CI job that
   runs the full user path on all three operating systems:
   write a handoff, validate it at HC-3, bind a contract, create a receipt,
   pass the result to Key through the adapter in the verification interface,
   and run Key's run verification. Add a negative run where a check fails,
   and confirm both layers report the failure.
6. Re-pin Key to 0.11.0b1 in spec/verification-interface.md and key-verify.
7. Add docs/compatibility.md with a table of Forge, extension, and Key
   versions tested together. The Key repository publishes the same table.
8. Set every spec's Status to Beta. Leave versions below 1.0.0, except the
   acceptance receipt spec, which stays at 1.0.0.
9. Reviewer pass: read all four specs, plus Key's trust boundary document,
   and list contradictions, undefined terms, and MUST-level requirements
   that have no check. Fix them or record them in the enforcement map as
   known debt.
10. Rewrite docs/getting-started.md as a beta user guide covering install,
    the first handoff, the first receipt, and optional Key verification.
    Update README and CHANGELOG, then release 0.9.0 per protocol rule 5.

## Forbidden Behaviors
- Do not modify or delete failing tests or checks to achieve a passing state.
- Do not mark an invariant as enforced without naming the check that fails
  when the invariant is violated.
- Do not describe the beta as stable or production-ready anywhere.
- Do not add features beyond this list; new ideas go to Deferred in the
  roadmap README.

## Output Format
A single pull request with the Validation Checklist results, the reviewer's
findings list from step 9, the `npm pack` file listing, and links to the
joint workflow CI runs on all three operating systems.

## Validation Checklist
- [ ] `forge validate --level HC-3` passes on an example with a matching
  contract and fails when a checklist item is not mapped.
- [ ] The invariant map test passes, and every INV entry has a check or a
  known_debt reason.
- [ ] The packed tarball installs into an empty directory and `forge --help`
  lists all four subcommands.
- [ ] The joint workflow job passes on ubuntu-latest, macos-latest, and
  windows-latest, and its negative run fails in both layers.
- [ ] key-verify passes against Key 0.11.0b1.
- [ ] Every spec shows Status Beta.
- [ ] All previously passing tests and harness scenarios still pass.

## Failure Recovery
If blocked: state what blocked completion, separate confirmed facts from
assumptions, leave existing formats and scripts untouched, propose the
smallest safe next step, and stop. If Key 0.11.0b1 is not released yet,
stop at step 5 and wait.
